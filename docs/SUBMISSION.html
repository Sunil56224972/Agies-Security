01   Problem & Solution Brief

The Autonomous SOC Problem

Why alert fatigue demands a self-directing agent — not another SOAR playbook.

Problem Statement

Modern enterprises face alert fatigue from high-velocity NIDS sensors (Snort, Suricata) generating hundreds of events per hour. Human analysts must manually correlate alerts with CMDB records, cross-reference CVE databases, parse endpoint logs, and enforce firewall containment — a process that takes 20–45 minutes per incident. During this window, adversaries move laterally, deploy ransomware, and exfiltrate data.

Target Users

Tier-1 / Tier-2 SOC Analysts overwhelmed by false positives who need intelligent triage automation to focus exclusively on confirmed threats.

Incident Response Teams requiring fast, auditable containment with full MITRE ATT&CK traceability.

Enterprise Security Operations seeking sub-5-minute MTTD and MTTR without expanding headcount.

Why This Problem Requires an Agentic Solution

Traditional SIEM/SOAR platforms execute fixed, pre-programmed rule trees. They fail when conditions deviate from the playbook — for example, when an exploit signature targets a runtime environment that is not installed on the target host. An autonomous agent is required because:


Multi-step dynamic reasoning — The investigation cannot be pre-scripted. Each tool call produces new evidence that reshapes the hypothesis.

Changed-condition replanning — When a Log4j exploit is fired against a Python/FastAPI server (no JVM installed), the agent must detect the mismatch and replan — not blindly enforce a block.

Objective verification — Containment must be confirmed, not assumed. An agent re-observes the environment post-action to verify defense state before closing the case.

Proposed Solution

Aegis Security — an enterprise SOC platform powered by a multi-turn ReAct reasoning agent (LLaMA 3.3 70B on Groq LPU) that autonomously ingests NIDS alerts, correlates CMDB and CVE intelligence, validates ground truth through server logs and EDR telemetry, enforces sandboxed Netfilter containment, objectively verifies defense state, and records auditable investigations in Neon PostgreSQL with MITRE ATT&CK mappings — all in under 3.2 seconds.

Expected Impact

MTTD < 1.4 seconds — from alert ingestion to initial classification.

MTTR < 3.2 seconds — from detection to verified containment.

Zero erroneous blocks — incompatible runtime detection prevents false containment actions on healthy hosts.

100% audit trail — every tool call, evidence observation, and verdict persisted in PostgreSQL with MITRE ATT&CK classification.

Investigation Workflow

GOAL — Operational Objective Received

Agent receives high-level goal: "Investigate ALERT-2026-9001. Determine if the Log4Shell attack against prod-web-core succeeded. Contain the threat. Record the verdict." No pre-scripted playbook — the agent decomposes the goal independently into a reasoning plan.

DECISION — Tool Selection & Sequencing

Agent reasons: which tools to call, in what order, with what arguments. Plan: ingest alert → decode packet → check CMDB → lookup CVE prerequisites → validate server and EDR logs → decide containment action.

ACTION — Tool Execution with Live Data

8 sandboxed tools called sequentially against live Neon PostgreSQL. Results include real CVE records, actual server log entries (HTTP 200, EDR process spawn), and live asset configurations. No mocked data at any step.

INTERMEDIATE RESULT — Evidence Synthesis

Server log shows HTTP 200 + EDR confirms java spawned /bin/sh reverse shell. Asset has log4j-2.14.1 installed. CVE-2021-44228 prerequisites fully match. Attack confirmed at 96% confidence.

ADAPTATION — Failure / Changed Condition (Criterion 6)

Scenario 6A: Separate Log4j exploit fired at Python/FastAPI host. CMDB shows no JVM or log4j package. Server logs return HTTP 401. Agent detects incompatible runtime stack → replans verdict to FALSE_POSITIVE → skips firewall block → zero erroneous traffic drops.

FINAL OUTCOME — Verified Containment & Audit Record

Firewall BLOCK rule enacted for 185.220.101.45. Defense probe confirms RST_SENT_PACKETS_DROPPED. Investigation verdict committed to PostgreSQL: MITRE TA0001 / T1190 — Initial Access / Exploit Public-Facing Application. Confidence: 96%.

06   Setup Instructions

Getting Started

Platform boots in under 30 seconds. Prerequisites: Node.js 18+, Groq API key, Neon database.

1

Clone the repository

bash
git clone https://github.com/Sunil56224972/Agies-Security.git cd Agies-Security
2

Install dependencies

bash
npm install

Installs all 7 runtime packages automatically.

3

Configure environment variables

bash
cp .env.example .env # Open .env and set GROQ_API_KEY and DATABASE_URL
4

Bootstrap the database — automatic on first boot

On startup, server.js automatically executes CREATE TABLE IF NOT EXISTS for all 11 tables and seeds baseline NIDS alerts, CMDB assets, CVE records, and server logs. No manual SQL steps required.

Manual option: Run init_db.sql directly in the Neon SQL Console for full DDL review.

5

Start the platform

bash
npm start # Expected output: # Server running at http://localhost:3000 # Sandbox Tools loaded: 8 # Model: llama-3.3-70b-versatile via Groq LPU # Database: connected (Neon PostgreSQL)

Open in browser — http://localhost:3000

07   Agent Tools

8 Sandboxed SOC Environment Tools

All tools interact bidirectionally with live Neon PostgreSQL. Zero static mocked responses at any point.

Tool 01
ingest_nids_alerts
Ingest and list Snort/Suricata NIDS events from the database. Returns alert signatures, source/dest IPs, severity, and raw L7 payload.
Tool 02
get_packet_metadata
Retrieve low-level packet metadata, protocol flags, decoded headers, and hex payload from the network sensor capture.
Tool 03
lookup_asset_inventory
Query CMDB for OS family, version, running services, installed packages, open ports, and WAF protection status.
Tool 04
query_cve_kb
Query the CVE Knowledge Base for CVSS score, affected products, exploit prerequisites, attack vectors, and remediation guidance.
Tool 05
query_server_logs
Retrieve HTTP access logs, auth logs, syslog, and EDR process execution trees to verify whether an exploit actually executed.
Tool 06
execute_firewall_action
Deploy a BLOCK or ISOLATE rule in the Netfilter sandbox to cut off attacker C2 communication or lateral movement paths.
Tool 07
verify_defense_state
Probe the Netfilter kernel simulator post-action to objectively confirm packets from the attacker IP are actively dropped.
Tool 08
record_investigation_verdict
Commit final evidence-backed incident report to PostgreSQL with MITRE ATT&CK mapping, confidence score, and actions taken.
